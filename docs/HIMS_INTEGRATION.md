# HIMS integration

MediBytes turns a recorded consultation into a six-section note and posts it to the hospital's
`audio_transcription_receive` API. This page is the contract: what the hospital calls, what we
call, and what each side cannot report.

```
HIMS --(1) POST audio + audio_id-->  MediBytes   (minutes: MedASR, Whisper, gpt-4.1)
HIMS <--(2) POST note ------------   MediBytes   (their receive API, when the job is done)
```

## 1. Sending a recording (HIMS to MediBytes)

`POST /api/v1/transcriptions`, `multipart/form-data`

| Field        | Type    | Notes |
|--------------|---------|-------|
| `file`       | file    | `.wav .mp3 .m4a .mp4 .aac .flac .ogg .webm`, at most 64 MB |
| `audio_id`   | string  | 1-64 characters from `A-Za-z0-9-` (a UUID is fine). Echoed back to you in step 2 |
| `company_id` | integer | Optional, default `1`. Echoed back in step 2 |

Header: `Authorization: Bearer <key>`. The key is generated by MediBytes and shared out of band
(`MEDIBYTES_API_KEYS` on the server).

Reply `202`: `{"audio_id", "company_id", "job_id", "status", "status_url"}`. The note is **not**
in this reply; it arrives at your receive API when the job finishes.

| Status | Meaning |
|--------|---------|
| 401 | Missing or wrong key |
| 413 / 415 / 400 | File too big / unsupported type / empty |
| 422 | `audio_id` not allowed |
| 503 | The server has no API key configured, or no OpenAI key |

Sending the same `audio_id` again returns the existing job and does not process anything twice.
If that earlier attempt failed, the new upload replaces it. The same recording under two
`audio_id`s is processed once and delivered twice.

## 2. What we post to HIMS

`POST <MEDIBYTES_HIMS_URL>` with `Authorization: Bearer <MEDIBYTES_HIMS_TOKEN>` and a JSON body:

```json
{
  "audio_id": "42ce7530-e963-456e-a72d-0a9d4cffbfb0",
  "company_id": 1,
  "response": "[{\"present_illness\": \"...\", \"examination_findings\": \"...\", \"previous_diagnosis\": \"...\", \"plan_of_management\": \"...\", \"diet_instructions\": \"...\", \"general_instructions\": \"...\"}]"
}
```

`response` is a **string** holding a JSON array of one object. All six fields are always present
and are strings: the items of that section joined with `; `, or `""` when the recording did not
cover the section. Items that restate each other ("fever" next to "three days of fever") are
reduced to the longer one. Wording rules applied to every note:

- A denied symptom reads `Denies fever`; a denied allergy keeps `DENIED allergy: ...`, a drug
  that was refused keeps `NOT GIVEN: ...`.
- A drug heard without a dose is written by name only (no "no dose" label), and the US name
  albuterol is written as salbutamol.
- A one-valued vital heard as two numbers ("pulse 100, 104 beats per minute", a restart) keeps
  the last one.

**The note is a draft for clinical review.** It is produced from speech recognition, so heard
words can be wrong ("now moderate exacerbation" can come out as "no moderate exacerbation"),
and a spoken duration or frequency ("daily for five days") is not always carried over. It
should be checked by a clinician before it is relied on.

A note that failed its own schema check is not sent (delivery state `failed`).

### What counts as delivered

The HIMS API reports failure in the body. We probed it with a wrong token: it answers **HTTP 200**,
`Content-Type: text/html`, body `{"status":"Failed","Message":"Unauthorized"}`. So:

| HIMS reply | We record | Retried |
|------------|-----------|---------|
| 2xx and the body is not `{"status": "Failed"}` | `delivered` | no |
| 2xx with `{"status": "Failed", "Message": ...}` | `failed`, message kept | no |
| 401, 403, other 4xx | `failed` | no |
| Cloudflare challenge (`cf-mitigated` or "Just a moment") | `failed`, "blocked by Cloudflare" | no |
| Network error, timeout, 408, 429, 5xx | `pending` | after 10 s, 1 min, 5 min, 15 min, 30 min, then `failed` |

## 3. Checking a delivery (HIMS to MediBytes)

HIMS's receive API has no field for errors, so a recording we cannot process is **never** posted
(an empty note would look like a real one). Poll instead:

`GET /api/v1/transcriptions/{audio_id}` (same Bearer key) returns

```json
{
  "audio_id": "...", "company_id": 1, "job_id": "job-...",
  "job_status": "queued | running | succeeded | failed", "job_error": null,
  "delivery": {"state": "pending | delivered | failed | job_failed", "attempts": 1,
               "last_http_status": 200, "last_error": null, "hims_reply": "...",
               "delivered_at": "...", "next_attempt_at": null},
  "response": "<the exact string that was or will be sent>",
  "needs_review": [{"section": "plan_of_management", "text": "Complete blood count"}]
}
```

- `job_failed`: the recording was rejected (silence, too short, unreadable) or the pipeline broke.
  `job_error` says why. Upload it again with the same `audio_id`.
- `failed`: we could not deliver. `last_error` says why. After fixing the cause (for example a new
  token), `POST /api/v1/transcriptions/{audio_id}/redeliver` pushes the same note again.
- `needs_review`: items the pipeline could not fully verify against the transcript. They **are** in
  `response`, because a plain string cannot carry a flag. A clinician should check them.

## Restrictions to know about

- **Failure is in the body of HIMS's reply** (above). We read it; any other client must too.
- **The `audio_id` must already exist in HIMS.** Their receive API updates a record they created
  when the recording was made; an unknown id answers `200` with
  `{"status":"Failed","Message":"Transcription record not found"}` (probed 2026-10-22 with a dummy
  id and the real token, so the token itself is accepted). We record that as `failed` with the
  message and do not retry. HIMS must send the same `audio_id` it created, not a new one.
- **Cloudflare sits in front of `himsapi.sriher.com`.** From a cloud host it may serve a challenge
  instead of reaching the API. If deliveries fail with "blocked by Cloudflare", HIMS has to allow
  this path or this server.
- **Their success reply is not documented.** We treat any 2xx that is not `Failed` as delivered
  and keep the reply text in `hims_reply`. Please confirm what a saved note returns.
- **Retries can duplicate.** If HIMS saved a note but timed out before replying, our retry posts it
  again. Please confirm whether the receive API is idempotent on `audio_id`.
- **One recording at a time.** The pipeline has a single worker; each recording takes minutes.
  Jobs queue in order.
- A restart of the MediBytes server re-runs any hospital recording that was still processing.
- Hospital recordings and notes are only readable through the routes above. They never appear in
  the demo UI's job list or file routes.

## Server settings

| Variable | Purpose |
|----------|---------|
| `MEDIBYTES_API_KEYS` | Comma-separated keys accepted on `/api/v1`. Empty means the routes answer 503 |
| `MEDIBYTES_HIMS_URL` | The full receive URL, `.../patinetcareop/audio_transcription_receive` |
| `MEDIBYTES_HIMS_TOKEN` | HIMS's Bearer token. Until both HIMS settings exist, notes wait as `pending` |

Delivery state is kept in `<MEDIBYTES_RUNS>/hims/<audio_id>.json`, on the persistent volume.
The demo UI and `/api/jobs` need no key and are unchanged.
